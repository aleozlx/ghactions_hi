### Open — please read before merging

**1. A correction to my own commit message.** `f6712cfd` claims the scoped-run banner goes "on the check a merge decision actually reads". **That is wrong.** It writes to `$GITHUB_STEP_SUMMARY`; branch protection and auto-merge read only the check-run *conclusion*. Worse, the signal I dismissed there as "easy to miss on a check list" — job names changing to `Targeted Unittest` — *does* appear in the checks list, so the mitigation is strictly less visible than the thing it called inadequate. Making it real requires changing the check's **name or conclusion**, which is a design call on this feature, not a patch.

**2. A scoped experimental request can degrade to a green that ran none of it.** `pytest.ini`'s `norecursedirs` keeps `tests/experimental/` out of the full suite, and the H100 full lane also excludes it, so the tree is covered only by the single explicit line in `task_jit_run_tests_part5.sh`. Every fallback route — prose, a `-k` selector, a backticked path, an over-cap request, a `::selector` — discards the scope and runs that suite. Benign today (part5 names the only experimental file); the moment a second `tests/experimental/test_<backend>.py` exists, someone scoping to it gets a green required check having run none of it. Note my `::selector` rejection **made this worse for the likeliest input**, converting a loud red into a quiet green. Fixing it means either failing *closed* when the text looks like an intended path, or giving the experimental tree its own lane.

**3. `ci-bot-commands.yml` is executed by zero CI runs.** `issue_comment` workflows load from the default branch, so nothing on this PR ever runs that file — it goes live only at merge. Every fix above in that file rests on hand-execution, not CI. A mistake there silently disables the repo's primary CI trigger for everyone, discoverable only by someone typing a bot command on `main`. Worth one human read, and worth someone running `@flashinfer-bot run tests/experimental/test_experimental_api.py` on the next PR immediately after merge.

Also unfixed by design: this workflow has **no bot-author guard** (`github.event.comment.user.login != '<bot>'`). Removing the trigger phrase from the one comment fixes today's instance; the guard would be the durable fix and covers any comment this workflow learns to post later.
